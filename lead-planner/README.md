# План лидобалов — сервис для маркетологов филиалов

Сервис ставит маркетологам филиалов план на месяц и на набор по **лидобалам**, лидам по типам и рекламному бюджету. Он подсвечивает филиалы, которые проваливают план, и переносит недостачу на следующий месяц.

- **Админка (вы):** все филиалы на одном дашборде. Провальные филиалы стоят сверху и выделены красным. Из списка можно перейти в любой город и посмотреть его план детально.
- **Маркетолог города:** свой логин, видит только свои филиалы, ведёт ивенты.
- Светлый интерфейс с дашбордами: KPI, темп по филиалам, план и факт по продуктам, месяцы набора, структура лидобалов по источникам.

## Методика

**1 лидобал = 1 ожидаемый оплаченный договор.** Балл за лид равен норме конверсии его типа в договор:

| Тип лида | Норма (лидобалов за лид) | Бюджет |
|---|---|---|
| Входящий звонок | 0,18 | органика |
| Заявка с сайта | 0,15 | CPL из FB |
| Лид-форма | 0,05 | CPL из FB |
| Мессенджер | 0,10 | CPL из FB |
| Заявка на обучение | 0,15 | органика |
| Демо | 0,05 | органика |
| Визит без заявки | 0,30 | органика |
| Регистрация на ивент | 0,08 | цена регистрации |

Нормы, признак «платный», доли по умолчанию и лимиты долей меняются в админке в разделе «Настройки». Нормы для мессенджера, заявок на обучение и визитов предварительные: сверьте их с отчётом CRM.

Расчёт на месяц ведётся по каждому продукту (форма обучения CRM):

1. **План лидобалов** = план договоров месяца × **90%** (минимальная норма для маркетинга) + **перенос недостачи** прошлых месяцев набора.
2. Из плана вычитаются лидобалы **ивентов** продукта (регистрации × 0,08).
3. Остаток делится по типам лидов в долях вклада. Если доли не заданы, берётся вклад источников в прошлом месяце, а если его нет, то доли по умолчанию. **Входящие звонки получают не больше 5%**, излишек уходит на остальные типы. Лимит задаётся колонкой «Макс. доля» в настройках.
4. **Лиды** по типу = лидобалы типа ÷ норма типа.
5. **Бюджет** = платные лиды × CPL продукта + регистрации × цена регистрации. CPL берётся из FB-кабинета города: расход кампаний продукта ÷ их лиды за 30 дней. Если таких кампаний нет, используется средний CPL кабинета, иначе CPL, заданный вручную. Коэффициент к CPL на филиал учитывает сезонность.

**Набор** — полугодие, как в CRM: I — январь–июнь, II — июль–декабрь. План набора берётся из CRM («план набора» по формам). Когда закрытый месяц недовыполнен по лидобалам, его недостача добавляется к плану следующего месяца того же набора. Недостача копится, пока план не догонят.

**Статус** считается по темпу: факт лидобалов ÷ (план месяца × прошедшая часть месяца).
- ≥ 100% — в плане;
- 85–100% — риск;
- ниже 85% — **провал**.

Пороги меняются в настройках. Если факта лидобалов нет, статус «Нет факта ЛБ», а перенос не считается.

## Данные

| Что | Откуда |
|---|---|
| План договоров на месяц по формам, факт договоров | CRM (план месяца) — `scripts/load-snapshot.mjs` или импорт |
| План набора | CRM (план набора) |
| **Факт лидобалов** | Заявки CRM по типам за месяц (отчёт по интернет-запросам: Facebook, сайт, курсы, консультации, заявки на обучение, AI-бот, ивенты) × норма типа. Спам и дубли не считаются. Точнее — выгрузка отчёта «Маркетинг → Лидобалы» через «Импорт» (по продуктам) |
| Цена лида | Примерная цена лида по типу (настройки) или своя для филиала (Ввод данных). FB-кабинет — необязательно |
| Ивенты | Вносят маркетологи / администратор |

Импорт понимает таблицы в «длинном» формате (филиал × месяц × форма) и в «широком» (колонки по типам лидов). Заголовки распознаются по словам «Филиал», «Месяц», «Форма», «Лидобалы», «Договоры», «Звонки», «Лид-формы» и т. п. Перед загрузкой файл можно проверить кнопкой «Проверить».

Факт для платных типов (сайт, лид-форма, мессенджер) подтягивается из FB, если для этого месяца нет данных отчёта.

## Запуск

Нужен Node.js 20+. Внешних зависимостей нет.

```bash
cd lead-planner
META_ACCESS_TOKEN=... ADMIN_PASSWORD=... npm start   # http://localhost:8787
npm test
```

| Переменная | Назначение |
|---|---|
| `PORT` | порт (по умолчанию 8787) |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | первый администратор; без пароля он генерируется и печатается в консоль |
| `META_ACCESS_TOKEN` | токен Meta Marketing API с правом `ads_read` на кабинеты городов |
| `API_TOKEN` | токен для автоматической загрузки `POST /api/import` и `POST /api/import/snapshot` |
| `REFRESH_MINUTES` | интервал автообновления, по умолчанию 600 (раз в 10 часов); 0 — выключить |
| `CRM_SNAPSHOT_URL`, `CRM_SNAPSHOT_TOKEN` | адрес, по которому сервис сам забирает снимок данных CRM (формат — `lib/snapshot.mjs`) |
| `DATA_FILE` | путь к хранилищу (по умолчанию `data/store.json`) |

Хранилище — один JSON-файл в `data/`. Эта папка исключена из git: в ней реальные планы и данные CRM. Делайте её резервные копии.

### Загрузка данных из CRM

```bash
node scripts/load-snapshot.mjs data/crm-snapshot.json 2026-10
```

Формат снимка описан в начале скрипта. Его можно собирать по расписанию из API CRM: план месяца, план набора и, когда появится доступ, отчёт «Лидобалы».

Автоматическая загрузка по HTTP:

```bash
curl -X POST http://host:8787/api/import -H "Authorization: Bearer $API_TOKEN" -H "content-type: application/json" -d '{
  "plans":   [{"branchId":"dp","month":"2026-10","productId":"form_ma","plan":25}],
  "facts":   [{"branchId":"dp","month":"2026-10","productId":"form_ma","balls":3.4,"contracts":1}],
  "seasons": [{"branchId":"dp","season":"2026-H2","productId":"form_ma","plan":165}]
}'
```

## Ссылка для показа (без сервера)

`node scripts/build-static.mjs <пароль> data/lead-planner.html` собирает одну HTML-страницу со всем интерфейсом и расчётом. Данные внутри зашифрованы паролем (PBKDF2 + AES-GCM): без пароля их нельзя прочитать даже из исходного кода. После ввода пароля выбирается роль: администратор или маркетолог конкретного города.

Правки, сделанные на такой странице, сохраняются только в браузере смотрящего. Импорт, обновление FB и выдача паролей работают только в серверной версии.

## Обновление данных

Отчёт показывает текущее состояние и обновляется сам:

- **Сервис обновляет данные раз в 10 часов** и при каждом запуске. Он перечитывает FB-кабинеты всех городов (расход, лиды, CPL) и снимок CRM по `CRM_SNAPSHOT_URL`, если этот адрес задан.
- **Данные CRM можно присылать со стороны CRM**, например ежедневным cron-заданием: `POST /api/import/snapshot` с токеном `API_TOKEN`. Тело запроса — снимок в формате `lib/snapshot.mjs`, в нём планы, факт договоров и лидобалы из отчёта.
- **Статус, темп и «ожидаемо к сегодня» пересчитываются при каждом открытии страницы** по сегодняшней дате.
- **Открытая страница сама перерисовывается каждые 5 минут.** Исключения — формы ввода и админ-разделы.
- **В шапке видно, когда данные обновлялись последний раз.** Зелёная точка означает, что обновление было сегодня. Подсказка показывает результат последнего прогона и ошибки FB. Администратор может запустить обновление кнопкой ↻.

## Доступы

В разделе «Доступы» администратор создаёт пользователя-маркетолога и отмечает его города. Пароль генерируется и показывается один раз; его можно сбросить. Маркетолог видит только свои филиалы, ведёт ивенты, смотрит план и скачивает CSV. План, факт, настройки и импорт доступны только администратору.

```
  lib/defaults.mjs     нормы, продукты, шаблоны кампаний FB
  lib/meta.mjs         Meta Marketing API
  lib/importer.mjs     импорт CSV/XLSX отчётов CRM
  lib/auth.mjs, store.mjs
  public/              интерфейс (HTML/CSS/JS, графики на SVG)
  scripts/load-snapshot.mjs
  test/
```
