# План лидобалов — сервис для маркетологов филиалов

Сервис ставит маркетологам филиалов план на месяц и на набор по **лидобалам**, лидам по типам и рекламному бюджету. Он подсвечивает филиалы, которые проваливают план, и показывает расход на рекламу по продуктам. Данные обновляются раз в день, в 8:00 по Киеву.

- **Админка (вы):** все филиалы на одном дашборде. Провальные филиалы стоят сверху и выделены красным. Из списка можно перейти в любой город и посмотреть его план детально.
- **Маркетолог города:** свой логин, видит только свои филиалы, ведёт ивенты.
- Светлый интерфейс с дашбордами: KPI, темп по филиалам, план и факт по продуктам, месяцы набора, структура лидобалов по источникам.

## Методика

**1 лидобал = 1 ожидаемый оплаченный договор.** Балл за лид равен норме конверсии его типа в договор:

| Тип лида | Норма (лидобалов за лид) | Бюджет |
|---|---|---|
| Входящий звонок | 0,18 | органика |
| Заявка с сайта | 0,15 | CPL из FB |
| Лид-форма | 0,05 | CPL из FB |
| Мессенджер | 0,10 | CPL из FB |
| Заявка на обучение | 0,15 | органика |
| Демо | 0,05 | органика |
| Визит без заявки | 0,30 | органика |
| Регистрация на ивент | 0,08 | цена регистрации |

Нормы, признак «платный», доли по умолчанию и лимиты долей меняются в админке в разделе «Настройки». Нормы для мессенджера, заявок на обучение и визитов предварительные: сверьте их с отчётом CRM.

Расчёт на месяц ведётся по каждому продукту (форма обучения CRM):

1. **План лидобалов** = план договоров месяца × **90%** (минимальная норма для маркетинга) + **перенос недостачи** прошлых месяцев набора.
2. Из плана вычитаются лидобалы **ивентов** продукта (регистрации × 0,08).
3. Остаток делится по типам лидов в долях вклада. Если доли не заданы, берётся вклад источников в прошлом месяце, а если его нет, то доли по умолчанию. **Входящие звонки получают не больше 5%**, излишек уходит на остальные типы. Лимит задаётся колонкой «Макс. доля» в настройках.
4. **Лиды** по типу = лидобалы типа ÷ норма типа.
5. **Бюджет** = платные лиды × **средняя цена лида $14** (настройка «Средняя цена лида для бюджета») + регистрации × цена регистрации. Если эту настройку очистить, цена лида продукта берётся из прошлого месяца: расход кампаний FB этого продукта ÷ их лиды (лид-формы, заявки с сайта, переписки). Кампании ивентов не учитываются. Если у продукта в прошлом месяце меньше 5 лидов, добавляются более ранние месяцы (до трёх). Если своей рекламы у продукта нет, берётся средняя цена лида филиала за прошлый месяц. Кампания относится к продукту по правилам «Расход на рекламу» (колонка «Форма CRM» в настройках). Ручная цена для продукта важнее всего.

**Набор** — полугодие, как в CRM: I — январь–июнь, II — июль–декабрь. План набора берётся из CRM («план набора» по формам). Когда закрытый месяц недовыполнен по лидобалам, его недостача добавляется к плану следующего месяца того же набора. Недостача копится, пока план не догонят.

**Оценка филиала** считается по темпу: факт ÷ (план месяца × прошедшая часть месяца). По умолчанию — **по лидам**: заявки CRM всех типов без спама и дублей против плана лидов. В настройках можно переключить на лидобалы.

| Темп к сегодняшнему дню | Оценка |
|---|---|
| меньше 30% | **Провал** |
| 30–60% | Недостаточно |
| 61–81% | Нужно усилиться |
| 82–100% | Неплохо |
| больше 100% | Выше плана |

Границы уровней меняются в настройках. Слабые филиалы стоят сверху; провальные и «недостаточно» выводятся отдельными строками над дашбордом. Если факта нет, статус «Нет факта».

**Качество лидов.** На главной и на странице филиала показаны доли от всех интернет-заявок CRM за месяц: удалённые (спам, дубли, другое), отказы и недозвоны — против сети. Доля подсвечивается, если она в 1,5 раза выше сети (и минимум на 5 п. п.). Удалённые заявки не входят в лиды и лидобалы; отказы и недозвоны входят — норма конверсии их уже учитывает. Источник — строка «ALL» отчёта по интернет-заявкам (`quality` в снимке, см. `lib/snapshot.mjs`).

**Что стало с лидами.** Там же — по истории заявок CRM (`crm_internet_requests`, `mode=history`): *отказ сразу* — первый результат обработки «отказ»; *отказ позже* — сначала недозвон, «думает», «перезвонить» и т. п., потом заявка закрыта как проигранная (с медианным сроком в днях); *не дозвонились сначала* → *потом дозвонились* (был хотя бы один успешный контакт) или *так и не дозвонились*. Доли — от обработанных заявок; удалённые и служебные типы не учитываются. Это не то же, что счётчик «отказ» в сводке CRM. Загрузка: сохранить все страницы истории за месяц (по 200 заявок, число страниц = `count_all` ÷ 200 — флаг `has_more` ненадёжен), затем `node scripts/lead-outcomes.mjs data/daily/crm-outcomes.json <филиал> <YYYY-MM> <файлы…> [-- …]` и `node scripts/load-snapshot.mjs data/daily/crm-outcomes.json`.

## Данные

| Что | Откуда |
|---|---|
| План договоров на месяц по формам, факт договоров | CRM (план месяца) — `scripts/load-snapshot.mjs` или импорт |
| План набора | CRM (план набора) |
| **Факт лидобалов** | Заявки CRM по типам за месяц (отчёт по интернет-запросам: Facebook, сайт, курсы, консультации, заявки на обучение, AI-бот, ивенты) × норма типа. Спам и дубли не считаются. Точнее — выгрузка отчёта «Маркетинг → Лидобалы» через «Импорт» (по продуктам) |
| Цена лида | Примерная цена лида по типу (настройки) или своя для филиала (Ввод данных). FB-кабинет — необязательно |
| Ивенты | Вносят маркетологи / администратор |

Импорт понимает таблицы в «длинном» формате (филиал × месяц × форма) и в «широком» (колонки по типам лидов). Заголовки распознаются по словам «Филиал», «Месяц», «Форма», «Лидобалы», «Договоры», «Звонки», «Лид-формы» и т. п. Перед загрузкой файл можно проверить кнопкой «Проверить».

Факт для платных типов (сайт, лид-форма, мессенджер) подтягивается из FB, если для этого месяца нет данных отчёта.

## Расход на рекламу

Раздел «Расход на рекламу» показывает по каждому филиалу Украины за выбранный период: **продукт — расход на рекламу — процент от всех затрат филиала**. Период выбирается месяцами «с … по …» или кнопками: текущий месяц, прошлый, 3 месяца, набор, всё время. Есть также сводка по сети, структура расходов филиалов и матрица «продукты × филиалы». Кампании продукта раскрываются по клику. Маркетолог видит только свои филиалы. На дашборде филиала есть такой же блок за выбранный месяц.

В таблицах есть колонки **«Договоры (CRM)»** и **«Расход на договор»**. Договоры — это все договоры формы продукта в CRM за период, включая органику и рекомендации: в CRM нет связи договора с рекламной кампанией. В итоговой строке — все договоры филиала и сколько из них пришло из интернет-заявок.

Продукт определяется по названию кампании FB. Правила задаются в «Настройках»: проверяются сверху вниз, побеждает первое совпадение. Ключ до 3 букв (шс, мка, ai) ищется как целое слово, длиннее — как часть названия. Кампании, которые не подошли ни под одно правило, попадают в «Не определено».

Расход загружается из файлов `data/spend/<филиал>.tsv` (строка: `YYYY-MM<TAB>расход<TAB>название кампании<TAB>лиды`; лиды нужны для цены лида по продуктам):

```bash
node scripts/load-spend.mjs data/spend 2026-10-13   # папка, данные по дату
```

## Запуск

Нужен Node.js 20+. Внешних зависимостей нет.

```bash
cd lead-planner
META_ACCESS_TOKEN=... ADMIN_PASSWORD=... npm start   # http://localhost:8787
npm test
```

| Переменная | Назначение |
|---|---|
| `PORT` | порт (по умолчанию 8787) |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | первый администратор; без пароля он генерируется и печатается в консоль |
| `META_ACCESS_TOKEN` | токен Meta Marketing API с правом `ads_read` на кабинеты городов |
| `API_TOKEN` | токен для автоматической загрузки `POST /api/import` и `POST /api/import/snapshot` |
| `REFRESH_AT`, `REFRESH_TZ` | ежедневное автообновление: время и часовой пояс, по умолчанию `08:00` и `Europe/Kyiv`; `REFRESH_AT=off` — выключить |
| `CRM_SNAPSHOT_URL`, `CRM_SNAPSHOT_TOKEN` | адрес, по которому сервис сам забирает снимок данных CRM (формат — `lib/snapshot.mjs`) |
| `DATA_FILE` | путь к хранилищу (по умолчанию `data/store.json`) |

Хранилище — один JSON-файл в `data/`. Эта папка исключена из git: в ней реальные планы и данные CRM. Делайте её резервные копии.

### Загрузка данных из CRM

```bash
node scripts/load-snapshot.mjs data/crm-snapshot.json 2026-10
```

Формат снимка описан в начале скрипта. Его можно собирать по расписанию из API CRM: план месяца, план набора и, когда появится доступ, отчёт «Лидобалы».

Автоматическая загрузка по HTTP:

```bash
curl -X POST http://host:8787/api/import -H "Authorization: Bearer $API_TOKEN" -H "content-type: application/json" -d '{
  "plans":   [{"branchId":"dp","month":"2026-10","productId":"form_ma","plan":25}],
  "facts":   [{"branchId":"dp","month":"2026-10","productId":"form_ma","balls":3.4,"contracts":1}],
  "seasons": [{"branchId":"dp","season":"2026-H2","productId":"form_ma","plan":165}]
}'
```

## Ссылка для показа (без сервера)

`node scripts/build-static.mjs <пароль> data/lead-planner.html` собирает одну HTML-страницу со всем интерфейсом и расчётом. Данные внутри зашифрованы паролем (PBKDF2 + AES-GCM): без пароля их нельзя прочитать даже из исходного кода. После ввода пароля выбирается роль: администратор или маркетолог конкретного города.

Правки, сделанные на такой странице, сохраняются только в браузере смотрящего. Импорт, обновление FB и выдача паролей работают только в серверной версии.

## Обновление данных

**Все данные системы обновляются раз в день, в 8:00 по Киеву.**

- **Серверная версия** обновляется сама каждый день в `REFRESH_AT` (по умолчанию 08:00, `Europe/Kyiv`) и при запуске. Она перечитывает FB-кабинеты городов и снимок CRM по `CRM_SNAPSHOT_URL`, если он задан. Данные CRM можно и присылать со стороны CRM: `POST /api/import/snapshot` с токеном `API_TOKEN` (формат — `lib/snapshot.mjs`).
- **Страница по ссылке** пересобирается ежедневным заданием Claude (Routine) около 7:45 по Киеву, чтобы к 8:00 данные были свежими. Задание через коннекторы CRM и Meta забирает:
  - план и факт договоров текущего месяца (`crm_plan_month_check`);
  - заявки CRM по типам с 1-го числа по сегодня (`crm_internet_requests`) — из них считается факт лидобалов;
  - расход кампаний FB текущего месяца по агентским кабинетам — для раздела «Расход на рекламу».

  1-го числа задание также закрывает прошлый месяц, а в начале набора (январь, июль) обновляет план набора. Затем оно загружает данные (`scripts/load-snapshot.mjs`, `scripts/load-spend.mjs`), собирает страницу (`scripts/build-static.mjs`) и публикует её по той же ссылке. Если хранилища `data/store.json` нет (новый контейнер), оно восстанавливается из опубликованной страницы: `node scripts/restore-static.mjs <страница.html> <пароль>`.
- **Статус, темп и «ожидаемо к сегодня»** пересчитываются при каждом открытии страницы по сегодняшней дате.
- **Открытая страница сама перерисовывается каждые 5 минут.** Исключения — формы ввода и админ-разделы.
- **В шапке видно, когда данные обновлялись** (время по Киеву) и когда будет следующее обновление. Зелёная точка означает, что обновление было сегодня. В серверной версии администратор может запустить обновление кнопкой ↻.

## Доступы

В разделе «Доступы» администратор создаёт пользователя-маркетолога и отмечает его города. Пароль генерируется и показывается один раз; его можно сбросить. Маркетолог видит только свои филиалы, ведёт ивенты, смотрит план и скачивает CSV. План, факт, настройки и импорт доступны только администратору.

## Структура

```
lead-planner/
  server.mjs           HTTP API + раздача интерфейса
  lib/planner.mjs      расчёт: лидобалы, лиды, бюджет, набор, перенос, статусы
  lib/defaults.mjs     нормы, продукты, шаблоны кампаний FB
  lib/meta.mjs         Meta Marketing API
  lib/importer.mjs     импорт CSV/XLSX отчётов CRM
  lib/schedule.mjs     ежедневное расписание (08:00 по Киеву)
  lib/auth.mjs, store.mjs
  public/              интерфейс (HTML/CSS/JS, графики на SVG)
  lib/spend.mjs        расход на рекламу: продукт по названию кампании, доли затрат
  scripts/load-snapshot.mjs, load-spend.mjs, build-static.mjs, restore-static.mjs
  test/
```
